# helm-d 自主逆向系统：研究与工程设计

> 设计稿；资料核对于 2026-11-22。尚未实现或验证新系统。适用范围：离线、可复制的二进制样本。

## 目标与研究假设

给定二进制、任务目标和固定计算预算，系统自主定位相关逻辑、形成可反证的假设、执行实验并交付带原始证据和复现输入的结论。允许“无法确认”为有效终态。待检验的假设是：相较现有 `deriveNextAction` 的顺序提示，实验反馈驱动的调度能提高独立判分的成功率和可复核率、减少无证据断言。这不是已观察到的提升。

论文级交付要求：任务集和独立评分器、固定预算的基线、逐步轨迹、消融、重复试验、置信区间与失败分析。模型的解释不充当真值。

## 当前底座与缺口

`packages/helmd/src/index.ts` 注册工具；`case.ts` 复制样本、建立磁盘 Case 和 E 编号；`tools/caseflow.ts` 记录假设并要求结论有 `evidence_ids`、`repro_cmd`；`autonomy.ts` 提示顺序下一步；`references/playbooks/reverse.yaml` 给出建议阶段。这是可复用的底座，目前没有实验候选队列、基于观察的选择器、自动独立验证和可量化停止条件。`persist.ts` 只自动保存包装后返回字符串的工具输出；外部 shell 命令的结果须显式 `save_evidence` 或由未来的执行适配器保存。`docs/design/AUTONOMOUS-RE-EXECUTION.md` 还明确规定 DSH 拥有 agent loop、helm-d 不另造循环，而且一次只开放一个假设；以下设计遵守这两个边界。特别注意：当前 `record_finding` 的自编证据门禁要求至少一条被引用证据由真实工具捕获，因此只用 shell + `save_evidence` 作为新适配器的输出通道可能无法通过现有门禁；实施 M2 前要验证并解决这个具体契约。

```
目标 + 原样本 → 复制/哈希/分诊 → 函数图与证据图 → 候选假设
             → 选择可反证实验 → 隔离执行 → 原始 E-id
             → 独立验证/反证 → 更新假设 → 继续/转向/停止
             → 可重放报告（包括覆盖与未知）
```

原样本只读，运行与补丁在副本中进行。模型自主决定下一步，但正确性由外部 oracle、独立工具或人工复核判定；所有行动限定在指定样本与预算内。

## 状态、证据与实验契约

Case 固定目标、样本 SHA-256、平台/工具版本和预算。新增追加式 `experiments.jsonl`；实现时需单写入者或原子写。每个事件记录：schema 版本、实验与假设 ID、问题/预测/反证标准、样本哈希、模块+RVA+镜像基址及文件偏移映射、方法（`static|trace|fuzz|symbolic|patch-on-copy`）、输入摘要、命令参数数组、工具版本、时间/内存限制、退出状态、观察（`supports|refutes|inconclusive|error`）、原始证据 E-id、验证器种类与独立验证 E-id。这是待实施的数据契约，不是现有 API。

证据图为“假设 H → 实验 X → 原始输出 E → 验证 V”。已验证结论至少要核对样本身份、可定位原始记录、实际运行过的复现输入以及独立复跑/负对照；一个 `repro_cmd` 字符串不代表复跑成功。缺少独立验证只能报告候选。跨版本函数身份先用样本哈希+地址，结构指纹仅作候选匹配。样本字符串、反编译文本和工具输出都是带来源标记的不可信数据，不能成为代理指令。

## 调度算法

可实施的每轮预测、选择、故障裁决与停止协议单列于 [autonomous-decision-loop.md](autonomous-decision-loop.md)；本节是概览，不代表相关 API 已实现。

1. 分诊格式、架构、哈希、节区/导入、保护迹象；高熵或异常入口先验证壳，再选动态分析。保留失败和原始输出。
2. 把任务映射到可观察行为；沿字符串交叉引用、调用图和有限数据流切片找候选函数，关键伪代码类型和分支返回汇编核查。
3. 每条假设包含预测、反证、依赖及成本。例：“此分支控制输入是否有效”，正负输入应走不同轨迹；无差异则削弱或反驳该假设。
4. 在满足前置条件的实验中，以“预期信息增益 × 相关性 × 可验证性 /（时间 + 工具成本）”作初版启发式排序，记录原因并限制重复。该公式及权重须消融，不能声称最优。
5. 先静态切片与小输入差分，再定点跟踪、限额 fuzz，最后针对明确阻塞分支尝试符号执行。保存 stdout/stderr、退出码、超时、轨迹及产物哈希。副本补丁带来的差异不能单独证明原程序语义。
6. 更新假设为支持、反驳或未定；独立验证成功才形成 verified finding。目标已达、预算耗尽、重复无增量或前提缺失时停止，报告覆盖与未知；压缩上下文后从磁盘恢复。

首版可用现有 shell 与 `save_evidence` 做手工调查与基线记录，但在 `requireToolEvidence` 门禁下，手工证据不能独自形成已验证 finding；M2 闭环需下文所述真实工具捕获适配器或经证实的宿主事件绑定。证明有稳定收益后再增加 Ghidra/Rizin/angr 的结构化适配器；工具不可用是一项观察，不进入无限安装重试。

## 可复现实验

任务集三组：A，自建、源代码已知的微型程序矩阵，覆盖编译器/优化/剥符号/架构/输入长度；B，有可执行 oracle 的外部基准任务；C，有维护者确认真值的真实开源二进制。公开校准集只用于开发，正式测试集在参数冻结后使用。按源项目和版本分隔并披露潜在训练污染，尊重数据许可；无外部真值的叙述性报告不计“解决”。

基线为当前 Case + 顺序提示；实验组添加事件账本和反馈调度。固定模型版本/温度、任务、工具镜像、网络、提示、token/命令/时间/提交预算。消融分别去掉证据图、反证步骤、预算调度、动态验证；跨模型重复以区分模型能力与系统效果。

主要指标：外部 oracle pass@1、干净环境复跑成功率、正确且有完整依据的 finding 比率。次要指标：关键函数 RVA 定位准确率、证据引用可解析率、错误肯定率、正确弃答率、时间/工具调用/token/成本、带来信息增量的实验比例。报告逐任务配对结果、重复试验置信区间和失败原因。剥符号、优化、错误反编译、加壳、损坏文件、超时、工具缺失、样本中夹带提示注入均纳入稳健性测试；不得将结果外推到未经测试的样本。

## 进一步设计：真正可研究的系统内核

上述“选下一步”公式仍过于抽象。系统的最小研究贡献应定义为 **证据约束的主动实验选择**：每轮根据已证伪/未解释的现象提出具体分歧实验，使相互竞争的机制假设产生不同的可观察预测；同时阻止把单一工具的推断误当验证。它与“多跑一些工具”的区别可以由反事实实验检验：拿掉证据约束后，如果成功率没有下降或错误肯定率没有增加，就没有理由宣称证据图对结果有贡献。

### A. 控制边界与事件语义

DSH 负责模型请求、工具调用和会话循环；helm-d 提供每轮可读取的**纯决策快照**和写入实验结果的工具。`suggest_next_experiment` 不执行命令；模型仍自主决定是否采纳，然后经现有工具调用。`record_experiment` 只接受完成后可查证的 E-id。不要另造第二个代理循环或外部 MCP；单 Case 一次最多一个正在执行的实验，候选可有多个，但只有一个 open hypothesis 对接既有 `record_hypothesis` 约束。每次快照以事件序号 `revision` 标识，写入时携带 `expected_revision`，发生并发/过期则显式报冲突并让模型重读。来源是现有单进程 Case 的扩展设计，不是对宿主原子性能力的断言。

状态采用 `INTAKE → MAP → TEST → VERIFY → REPORT`，另设 `BLOCKED` 和 `INCONCLUSIVE` 终态。阶段并非强制完整遍历：任何阶段可因新证据退回 MAP；VERIFY 失败必须重新 TEST 或以 UNKNOWN 收束。进展判据为**可观察差异**，不是模型感觉“有收获”：新增可定位函数/边、反驳已有假设、排除候选集合、得到新分支覆盖、验证一项结论，才算有增量。相同工具+参数重复不会自动增加进展。

每个实验事件至少具有 `proposed → reserved → running → observed → verified|refuted|inconclusive|failed` 状态。`reserved` 按样本哈希、命令+规范化参数、输入摘要计算去重键；只有 `observed` 带原始 E-id。崩溃恢复时 `running` 不能直接宣称失败或成功：查看进程退出记录/输出后补录，无法确定则转为 `inconclusive` 并说明证据缺口。证据写入成功后才能推进状态；防止记录“已验证”但附件未落盘。存储采用临时文件+原子替换或单写入者日志，读取时显式区分不存在的旧 Case 与损坏的新账本；当前 `loadHypotheses` 对解析异常返回 `[]`，不能将这一模式直接复制给新账本。

### B. 结构化观察和跨函数推理

建立三层图而不把所有伪代码混作一个节点：**程序图**（模块、函数、基本块、直接/间接调用、数据/控制依赖）、**证据图**（每条边的来源、版本、E-id、地址范围）和**争议图**（假设、相反预测、失败反例）。静态工具报告的间接调用目标标为 candidate；只有运行轨迹或经核查的值域约束可提升其确定性。一个采样输入观察到目标 A 只能证明该输入下可达 A，不能排除目标 B。

定位函数时先生成“输入/输出锚点”，如输入解析、长度检查、比较函数、成功/失败输出。反向切片从输出/返回点追到控制条件，正向切片从输入追到候选条件；交叉位置进入候选集合。对每个函数保留分析器版本、模块哈希、RVA、调用者/被调用者和未解析边，不记录未经验证的自然语言名称为事实。需要验证跨函数链时，给出 `source RVA → 调用边 → sink RVA` 及每段 E-id；间接边若未知则整条链标候选。这样 ICALL-BENCH 类型任务才能精确衡量进展。

对反编译器冲突建立明确裁决协议：如果伪代码与汇编、两个后端、或动态轨迹相矛盾，生成一条 `conflict` 事件，保存双方原始输出及地址。优先核查原始指令、重定位/加载基址和指令边界，再对具体输入做动态差分；仍无法裁决则保留两种解释，不合并为单一结论。“独立验证”指不同失败模式的证据来源，例如静态预测与动态轨迹或独立实现的解析器；同一反编译结果的两次 LLM 解释不算独立。

### C. 可落地的实验选择器

把“信息增益”改为可计算的有限集合指标。针对候选机制 `H={h1...hk}` 和可选实验 `a`，模型须提交每种结果对每个假设的预测（例如 `branch_taken|branch_not_taken|timeout`），并指出哪对假设会被区分。令 `split(a)` 为预测不同的假设对数量除以全部假设对数量；单一假设场景用“预期结果能否反驳该假设”替代。排序首先过滤安全可执行性、输入可用性、前置证据、重复键和成本上限，再按 `score(a)=split(a) × replayability(a) × relevance(a) / estimated_cost(a)` 排序。同分选较低成本、最后按稳定 ID 排序。模型对预测缺项时该实验不能进高优先级队列；估计成本不是实际成本，执行后用真实耗时更新下一轮。`split` 只能衡量提案内部的辨别力，不能证明预测正确；评测需检查预测校准率。

停止规则设两层：硬停（用户预算/总墙钟/工具超时/显式目标达成）与软停（最近 K=3 次独立实验均未缩小候选集、没有新边/分支/反例，且下一实验估计收益低于成本）。K=3 是待调参的工程默认值，评测里须保持固定并消融。停止时列出候选假设、每个未解原因、还能改变结论的最小实验和预期代价。防止把“没看到行为”写成“行为不存在”：记录观察窗口、输入、沙箱能力和检测下界。

### D. 示例：为什么需要区分实验

任务：已剥符号 ELF 的输入序列经过三层函数后决定输出 `OK`；静态工具把间接调用边指向函数 A 和 B。当前数据只证明 `OK` 字符串被引用，不能推断判定逻辑。

1. 假设 H-001：A 比较原始输入；H-002：B 比较经变换的输入。由于现有 Case 只允许一个 open hypothesis，两项先作为候选机制存于实验快照，再将本轮主问题登记为 H-001；H-002 留在候选集中。
2. 实验 X-001：构造长度相同但只改一字节的两个输入，追踪调用目标、参数摘要及成功/失败路径。预期 H-001 下 A 的入参/路径随输入变化；H-002 下 B 的变换结果和路径变化。原始命令、输入摘要和两次轨迹各自入 E-id。
3. 若轨迹仅显示调用 B，更新 H-001 为 refuted，登记 H-002，并以对变换前/后的字节作受控差分验证；若追踪器无法捕获间接调用则标 inconclusive，转而核查调用点的指针赋值与值域，不得声称 B 已被证实。
4. 取得接受输入后，复制原始样本到干净环境复跑有效/无效输入，记录两种返回码及输出。报告给出源输入到间接调用再到输出的带地址链；未覆盖的其他调用目标仍列未知。

这个场景产生可判分中间目标：间接调用目标集合、接受输入、负对照，以及用错追踪器时的正确弃答；不依赖“解释看起来合理”。

### E. 打通现有门禁的最小实现切口

从 `tools/caseflow.ts` 与 `persist.ts` 看，直接 shell 的输出经 `save_evidence` 会被标 `manual_`，而 `record_finding` 在 `requireToolEvidence` 开启时至少要求一条非手工捕获证据。M2 的首个实现应增加**一个**可审计的本地分析执行入口：只接受预定义后端 ID、参数数组、Case 内副本路径、预算；它调用本机工具、写原始 stdout/stderr/退出状态为 E-id，并以工具捕获来源注册。不得靠重命名 `manual_` 来绕开门禁；扩展 `record_finding` 时必须校验执行事件及证据哈希关联。首版后端可先用已装的系统 `file`/`objdump` 或项目内置工具，避免为了跑通最小闭环安装大型栈。若宿主 shell 已提供可验证的原始调用事件，也可考虑从真实 session log 捕获它；需先证明事件能够绑定输出文件和输入摘要。

对应三个小型接口：`case_status` 读取决策快照；`suggest_next_experiment` 只返回候选、排序和理由；`run_case_experiment` 执行有预算的预定义适配器并写 E-id。`record_hypothesis`/`update_hypothesis`/`record_finding` 保留现有名称与语义，新增验证状态通过持久化链接关联。所有由参数构造的路径先经 `assertWithinRoot()` 等价校验；Case 记录事件版本，旧 Case 默认没有实验账本，不做猜测性迁移。不要依赖 stdout 文本里的“成功”字样判断进程成功：同时核对退出码、文件产物与独立 oracle。

### F. 更严格的论文实证要求

研究主张拆成三条：R1 自主选择是否比顺序提示提高 pass@1；R2 双证据/反证是否降低错误肯定；R3 结构化跨函数图是否提高间接调用恢复率。分别给出对应消融（关调度、关验证、关图检索），每条主张都允许实验否定。将“看过的题”与保留题分组；模型先只读任务描述的 description-only 基线可检测记忆捷径；变换名称、常量和构建参数测试对表面线索的敏感性。评分器只收结构化答案（例如 RVA 集合、候选输入和置信层级），隐藏真值，不让模型依据评分反馈反复调参；评测次数和预算固定。

参考 Reveree 的思路，把失败按分诊、定位、解释、实验设计、执行、验证、报告归因，但中间里程碑以工具日志、地址及外部判据优先；如果需人评/模型评，盲化最终结果、双人标注并报告一致性。报告每个样本的成功与否、错误肯定、弃答、成本和阶段失败，按同一程序的变体聚类计算区间，避免把同源变体当独立样本。先设计评分规则再收集实验结果；任何显著性检验只能附在公开的原始逐任务结果之后。

这套内核的最小可证伪演示是：同一保留样本、相同预算下，系统从两个冲突的候选机制中选择一项能区分它们的实验，执行后正确更新假设，干净环境复跑其结论；随后人为使追踪工具失败，系统改为 inconclusive 且不写 verified finding。演示成功仍只是功能验收，不能替代规模化比较。

## 再次调研后收紧的四项验证规则

### 1. 把正确性分成三个不同问题

**任务答案**：给定输入是否被原程序接受、指定行为是否在原程序里发生；用原程序作为 oracle。**局部解释**：报告的函数地址和调用边是否与执行轨迹/反汇编一致；用指令级定位与可观察路径验证。**重新实现的语义**：代理复写算法或生成等价代码是否对合法输入保持行为；在同一输入集上比较原始和重建程序。三者不能互相替代：解出一个口令不等于正确解释所有分支，通过附带用例也不等于函数等价。

针对第三项，设计 `differential-check`：给定原始目标与候选实现、相同输入及明确的环境模型，运行两者并保存输出/返回码/崩溃/内存副作用的规范化差异；再从已有输入变异、覆盖反馈及约束边界生成新输入。任何差异都是反例并降低该候选结论的状态；没有找到差异只表示“在已测输入上未发现分歧”，不能声称形式等价。无法以一致 ABI、外部依赖和环境运行两端时标为 `inconclusive`，不得把仿真对不上归罪于程序逻辑。若采用静态等价检查，必须记录求解器假设和未知返回，证明义务是受限模型内的等价。

### 2. 在任务 manifest 中写出“可观测边界”

函数级题至少保存完整二进制或可核查的调用点、数据段、重定位信息、ABI/架构、依赖版本及驱动/包装器。缺少函数体外常量或参数类型不确定时，在输入阶段打 `missing-context` 标签，禁止与完整题汇总成同一个成功率。动态样本要保存运行环境、输入通道、可用系统调用、网络/时钟/随机数处理、超时和日志窗口。**未观察到行为**仅限于该边界；不能推出样本普遍不含此行为。

另设评分器自检：对每个题运行至少一个正例、一个负例、一个故障注入；正例不通过的题先修评分器。对于可执行 oracle，把模型可见反馈和最终判分隔离，以免代理通过反复提交读取隐藏答案。对同一源项目的变体按组拆分和统计，不把 100 个高度相似编译产物当作 100 次独立成功。

### 3. 证据独立性按失效模式计算

两份 E-id 可能来自相同底层分析器或同一次运行：引用数量不是独立性的度量。新账本为证据保存 `origin_run_id`、采集器、输入摘要、样本/镜像哈希、派生父 E-id。相同运行的反编译与其函数摘要属于一个静态证据簇；同一次跟踪的截图和导出文本属于一个动态簇。只有失败模式足够不同且产生新观察时，才将它作为第二种验证路径，例如静态分支预测 + 原程序输入差分。两个模型复述同一伪代码不会增加证明强度。现有 finding 对高严重度至少两条 E-id 的规则保留，但研究报告另算证据簇数与实际独立验证率。

### 4. 把失败归因落实为可复核事件

每次停下都记录最早阻塞位置：`input-invalid`、`environment-mismatch`、`triage-wrong`、`localization-wrong`、`semantic-misread`、`experiment-nondiscriminating`、`tool-failed`、`verification-failed`、`budget-exhausted` 或 `unknown`。分类要求对应事件号和 E-id；多原因时记录主因与次因，盲化最终答案供复核者标注。检验 R1/R2/R3 之外，再观察“省下的预算是否只是因为代理过早弃答”和“更多工具是否实际增加错误肯定”。这决定系统是否值得扩大工具面。

当前优先级因此调整为：先在 M0 加 oracle/manifest 自检和污染检测；再在 M1 记录来源簇；M2 才评估差分执行的价值。大规模静态等价或多后端并行放到 M3 后且以验证收益为前提。上述修改是设计，不代表新增工具已存在。

### 可复用结构：带就绪度和退路的技能声明

从五包抽象出的技能不是“只要文件存在就可调用”的文本块，而是下面一组可检查条件：`id、版本、来源哈希、适用格式/架构/壳签名、必须的输入、工具版本/依赖、预检、操作步骤、产物、失败分类、验证层级、退路、个案参考`。角色与不变量可以写入公共技能；偏移、指令字节、文件名、假设性的函数名保持在 Case 内，不能随案例硬编码进通用规则。

运行状态拆分：`indexed`（可检索）→ `readable`（正文可读取）→ `dependencies-ready`（工具/环境检查通过）→ `sample-matched`（当前样本签名匹配）→ `executed`（运行并留证）→ `validated`（输出经消费工具/目标环境验证）。任何阶段失败报告具体缺口与下一条可执行退路；特别不能把 `readable` 或解压命令返回 0 等价于 `validated`。只有最后两层能形成工具执行事实；报告仍须审查证据是否支持所写结论。

对于解壳产物建议细分成：`raw-decompressed`（解码得到非空字节）、`structural-ELF`（ELF/PHDR/LOAD/DYNAMIC/重定位边界均可解释）、`analyzable`（第二个消费工具能解析并定位代码）、`loader-accepted`（目标设备/模拟环境能加载）、`behavior-replayed`（同输入的关键业务路径与基线可对比）。overlay、缺失 LOAD gap、截断块和反调试都能使这些层级分离；必要时保存 bare 与 with-overlay 两种派生物，分别注明用途和哈希。无原始样本或可用设备时如实停在低层，不宣称脱壳完成。

M0 可加入专项保留任务：原版/变体壳的识别与拒识；一条缺 LOAD 空洞的损坏 dump；一条有 `/proc/self/exe` overlay 依赖的样本；一条假 0x1f4 块表；一个不存在依赖但技能文件可读取的安装环境。比较“只读取技能文本”与“分级预检+输出验证”在误报和正确弃答上的差异。完成后才考虑把这些个案脚本作为可选后端适配器，而不是随文档自动运行。

## 前置阶段 M-1：审计、精简并重写现有逆向技能库

### 文档三层架构与草案规范

1. **入口卡（短）**：从任务选分支，含 `when-to-read、first-observation、next-reference、not-enough-evidence`；目标 60–120 行左右，数字是待测试的可读性预算，不是硬上限。未知样本入口必须能从 `route_task` 一次触达。
2. **技术技能（按条件加载）**：一个清晰的触发信号 + 可反证的目标 + 前置条件/依赖 + 步骤 + 每步产物/失败分支 + 验证层级 + 停止条件 + 版本/平台差异。优先更新现有技术文档的归属与标题，仅在无法表达独立对象（例如 Android ELF 与 DEX）时新增文档。示例命令必须能与当前工具 schema/脚本参数匹配；不会在所有平台运行的命令标明平台。
3. **个案与原理（深度）**：保留调试轨迹、算法变体、工具脚本和特定样本值，开头标记来源和适用样本；不纳入通用入口优先读列表。跨个案可复用的只有角色、定位方式、失败模式和验证；固定地址留在个案内。

每份“技术技能”建议头部有稳定 ID、版本、维护者/来源、本地路径、适用对象（格式/ABI/保护类型/输入通道）、可观察触发条件、必要工具、预检、首个产生 E-id 的动作、成功验收和 fallback。拒绝只有关键词的触发：若 PE 的“UPX!”是唯一信号，只允许进入候选分析卡；若签名缺失但 ELF PHDR/loader 呈自读 overlay，则仍应有通往适当变体的路由。文本里的危险命令、外部链接及样本字符串都当数据读，不把它们当运行时指令。

### 逐篇裁决：保留、改写、迁移、归档

对每个候选文档制作 `inventory` 记录：路径、H1、行数、所属域、引用来源、是否由运行时路由、声称的工具命令、重叠段落、样本特异常量、验证强度、保留原因及目标入口。按句子而不是文件处理：可核对且唯一的内容保留；已过时命令直接纠错；重复流程保留一个规范入口，其他文档链接规范处；硬编码个案搬到案例；缺少证据的“总是/100%/必须”降为有前提的候选。旧文档不是无条件删除：对路径被引用的内容先改向/保留短过渡入口，再按索引与引用检查处理。旧 Case 已有绝对路径的引用仍需可解释。

优先级按 `错误传播风险 × 实际路由触达 × 重复度` 排序：P0 是工具名和验证断言、壳判别、DEX/ELF 区分；P1 是类型命名、动态失败与止损；P2 是个案整理和措辞。先修 P0，不把“压缩篇幅”当成正确性的替代目标。最小审阅单位为一组具体用户问题（未知 ELF、已保护 AArch64 ELF、Android APK DEX、GUI 校验、纯静态 C++ 结构重建），针对每组画 `route_task → read_reference → 首条证据 → 验证参考` 的实际路径，找断点和重复阅读。
