# 保护样本的升级与恢复协议（设计，未实现）

> 回答三个独立问题：**何时转动态？实际保护了哪一层？目标字节如何恢复与验证？** 本文是待实现的决策合同，不声称已经分析过具体样本或识别其加密算法。前置的技能审计见 [reverse-skill-audit-protocol.md](reverse-skill-audit-protocol.md)。

实现状态与已落地/待实现流程见 [protection-implementation-flow.md](protection-implementation-flow.md)。以下条目不能因为出现了部分路由代码就被视为完整执行。

## 一、输入和首轮限额

先固定任务：要回答的是“目标行为/输入”还是“解释保护器本身”？先记录文件哈希、格式、架构、可运行环境、入口和节/段/LOAD 映射、字符串/导入、覆盖观察窗口、是否有合法副本与基线。危险或未知程序只在隔离环境和副本运行；不能跑则保留纯静态路线。首轮最多两次目标导向的静态定位尝试（例如输入/输出锚点追 xref、入口/装载链追源数据），产出候选 RVA/证据或记录失败原因。不是“二次失败即必须运行”：转动态还要求可运行、隔离、可观察、有明确要测的转移或输入。

保护类型与算法分别标记：`suspected`（签名/熵）、`structural`（映射/写入/控制转移证据）、`observed`（实际执行或经校验的离线变换）。签名、段名、熵只能提出候选；普通压缩资源、数据加密、剥符号、正常解释器和无法定位的工具错误都可能假扮加壳。已知壳也必须做此构建的结构匹配，不能把产品名推广为固定密钥或固定算法。

## 二、何时升级观测通道

| 观察及待解问题 | 首选下一个动作 | 动态的具体触发/退路 | 不能做出的推断 |
|---|---|---|---|
| 静态能找到目标代码和输入到输出的链 | 静态切片、汇编交叉核查；若行为断言再做原程序正负对照 | 只有关键状态依赖运行时输入/装载后地址、静态工具冲突或静态链不可判分，才做针对性的 trace | 高熵资源不能推翻已定位的目标代码 |
| 入口 stub 写入/解压可执行区，目标函数在磁盘上不可见 | 保存写入范围/源范围与控制转移候选，提出“写后执行”的实验 | 隔离可运行、能捕获映射/写入/控制转移时，记录转移前后映射和字节；不必先识别壳产品 | OEP、完整 dump、解密完成均不是仅由高熵推出的 |
| 动态生成/JIT/自修改、分层 loader | 用区域版本和事件关联写入→执行；每次变换保留 parent hash | 当静态只有调度器/解释器且目标输出在运行时出现；若动态盲区则退回写入点/字节码静态切片 | 一次 dump 不代表所有阶段、所有输入 |
| 局部 VM、控制流平坦化、普通解释器 | 先定位受保护函数及输入/输出边界，再用切片/差分取语义 | 只有具体路径或寄存器/VM 状态不可静态裁决时才定点跟踪 | 不必假设存在可 dump 的“原始 ELF/PE” |
| APK/DEX/native FFI 或子进程加载 | 先列实际装载对象、调用边和对象身份 | 观察 `dex`/native 映射、加载时机与目标输出；按对象格式分开采集 | DEX dump 不是 ELF 解包；一个进程的 dump 不等于整个应用 |
| 签名命中但无装载变换迹象 | 寻找第二种独立结构证据，或先直接分析目标代码 | 仅因静态目标不可达且有可检验的运行时转移时升级 | 不将 UPX 字符串、节名或 `entropy > 7` 当已确认壳 |
| 运行不可信/缺依赖/观测器故障 | 解释静态 stub、验证离线解码与偏移映射，记录局限 | 没有可控沙箱或监测能力时不运行；换采集方式也要预算和有效性检查 | 监测器没有看到执行，不等于不存在执行 |

转动态必须有一张事前实验卡：`被哪个静态证据阻塞 → 要观察哪次加载/写入/比较 → 对两个候选机制的不同预测 → 观测窗口/仪器自检 → 超时与改向`。如果不能填写“动态要判别什么”，先补定位证据，不以“动态更强”为理由盲跑。转动态后如观测失效，错误归于观测器或环境，不能自动反证机制。

## 三、先确定被保护的对象，再选恢复方法

把保护现象建模为一个有向变换图：文件范围或资源 `source` →（搬运/解压/解密/生成/解释）→ 运行时范围或 VM 状态 `destination` → 调用目标/输出；每条边记录指令/RVA、写入范围、输入依赖、时机、证据 E-id 和未解变量。先回答任务是否需要**恢复原字节**：只需判定某个输入的行为时，输入/输出差分可能足够；需要拿到可分析代码或解释保护实现时，才升级到还原变换。

| 实测变换类别 | 下一步该判别的量 | 恢复方案与合格证据 |
|---|---|---|
| 结构完整且与已知解包器匹配的压缩壳 | 本构建头/块表/压缩方法、源/目标长度、overlay/导入与 loader 依赖 | 在副本上使用对应工具；记录版本、输入/输出哈希、失败码，校验解包结构和目标行为。不匹配时降级为未知变体，不能试图改几个签名字节就宣布成功 |
| 块压缩/修改 UPX/NRV 类 | 块边界、各块输出长度与上限、校验字段、窗口/字典初始化是否匹配 | 在**输入已识别**时尝试对应变体解压；逐块边界/长度/校验、PHDR/LOAD/DYNAMIC/overlay 和第二解析器验证。不存在可验证匹配则转入 stub 单步语义，不把 NRV2B 当壳家族的通用结论 |
| XOR/ADD/轮转或多轮流式变换 | 实际读/写循环、单位宽度、状态更新、密钥来源、每轮次序、边界与终止条件 | 对同一地址区间对比变换前后字节，复现两组独立块的输出及末块处理；有外部/运行时派生密钥时必须记来源，不能从单个明文片段硬猜常量 |
| 标准或自定义密码学加密 | 调用链或指令证据、模式/IV/nonce、填充、密钥生成与所在阶段 | 先定位密钥/输入在本次运行的真实来源；如需只回答行为可在解密后、使用前抓取受控内存片段；独立重实现必须对多输入比较且标注环境依赖。没有密钥/上下文就报告缺口 |
| 运行时 JIT/自修改/重定位 | 页面写入→执行序列、镜像基址、重定位和多版本字节 | 保存每个版本的范围与 parent hash，按实际目标分析；dump 必须说明取样时机、输入与映射，禁止视为唯一稳定“原始文件” |
| 字节码解释/函数级虚拟化 | dispatcher、handler、字节码来源、VM 状态和与原任务关联的输入/输出 | 只恢复目标函数的语义切片或 VM 操作集合；不强制寻找 OEP，也不把 VM 字节码叫作加密 ELF |

上述是**观测类别→候选办法**，不是“哪个产品用哪种算法”的字典。即便 UPX、Themida、VMProtect 等名字出现，也只有对**当前样本、当前保护层、当前构建**的源/目标与状态边有实测证据，才能说“这里使用了哪种变换”。若题目仅提供产品名而未提供样本或版本，不能推出密钥、算法或恢复成功。

## 四、恢复的升级门槛

每个产物标记最强已达级别：`captured-bytes`（有时点和映射的真实内存）→ `structural`（可解释头、程序头/节、LOAD gap、重定位/导入边界）→ `analyzable`（独立消费工具能定位目标代码）→ `loader-accepted`（目标环境可加载）→ `behavior-replayed`（同一受控输入正负对照可复跑）。某任务可以接受较低级别，比如只要某次运行的解密字符串；但不能用较低级别暗示更高一级。每次只允许在目标问题相关的区域或阶段扩大采样，不因“加壳”二字自动 dump 全进程。覆盖不足时保留原本未知。

## 五、将路由变成可测试门禁

现有 `packages/helmd/references/native/packer-handling.md` 有“定位 OEP 后立即 dump”“静态最后手段”“无法运行也算静态最后手段”和“file 类型正确即进入后续”的强制表述；`protection-detection-methodology.md` 有“VMP 必须动态”“TUSI 必须 Frida”等按产品名跳结论。`playbooks/triggers.yaml` 以熵和 imports 触发解包建议。这些文本均是**待审计的知识素材**，不能直接当路由器真值。现有自主设计只写“高熵或异常入口先验证壳”，并未给出上面的可执行分流、算法证据及恢复级别；因此答案是尚未做成。

实施前先用保留任务检验：假 UPX 标志+普通压缩资源、修改 UPX 块表错误、部分虚拟化而无整体 OEP、一次运行仅解密部分代码、无运行条件的 ELF、自读 overlay 的 loader、损坏 dump 被 `file` 接受、观测器丢事件。每题给出预期分流、可证实的目标范围、正确弃答与必要下一步；评测代理选错路径率、虚构算法率、无谓动态率、过早 dump 率以及各产物级别误报率。与同预算顺序提示配对比较，失败则修改规则，不把规则写成 persona 的绝对命令。
